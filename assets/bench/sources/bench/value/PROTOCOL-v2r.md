# Value benchmark protocol, version 2r (re-run of the 8 v2 tasks)

Written 2026-11-14, before any preparation, rehearsal or paid request for this version. This file is the
pre-registration of a re-run of the published 8-task benchmark (`PROTOCOL-v2.md`) with the current generator.
`PROTOCOL-v2.md` and its published results are not changed by this version. Any change to this file after its
first SHA-256 was recorded goes in the change log at the end, with the reason, and every recorded SHA-256 is kept.
Nothing here is chosen from outcome data of this version.

## What this is, and what it is not

These are **development tasks**. The same 8 tasks were used in the v2 scored run, its re-run after the refusal
fix, the Gate 1 rehearsal and later generator work, and the generator was changed while looking at results on
them. This includes the three `pallets/werkzeug` tasks that `PROTOCOL-v2.md` called held-out: later generator work
saw their results, so no task here is held out. The result can show whether the current generator helps or hurts
on tasks it was tuned on. It cannot show that it helps on unseen repositories, and the report says so next to the
numbers.

## Questions

1. Does the current default export (`olivium`) make Claude Code use fewer tokens, cost less or solve more than no
   harness (`none`)?
2. Do the generated skills and subagents matter: `olivium` against the same export without them (`olivium-nn`)?
3. How does `olivium` compare with Claude Code's own `/init` file (`generic`)?

## Arms

| Arm | What the agent gets | Settings and permission mode |
| --- | --- | --- |
| `none` | The repository at the commit before the fix. No instruction files. | `arms/benchmark-settings.json`, `bypassPermissions` |
| `generic` | Same, plus a `CLAUDE.md` written by Claude Code's own `/init` at that commit. | `arms/benchmark-settings.json`, `bypassPermissions` |
| `olivium` | Same, plus the output of `bin/harnessforge generate PATH --runtime claude_code --export DIR --json`, unmodified. No `--context` and no `--native` flag: the generator's defaults (lean context, generated skills and subagents, `--native all`). | the exported `.claude/settings.json`, byte for byte, with `--settings`; `default` |
| `olivium-nn` | Same as `olivium`, generated by the same application snapshot on the same input with `--native none` added: no generated skills or subagents. | the exported `.claude/settings.json` of this export, byte for byte, with `--settings`; `default` |

- Every arm starts from the same snapshot. Instruction files already in the repository (`CLAUDE.md`, `AGENTS.md`,
  `.claude/`, `.cursor/`, `.github/copilot-instructions.md`) are removed from every arm first, at any depth
  (`arms/entry.sh`), as in v2.
- `olivium` and `olivium-nn` are built at $0 by the runner (`run.py prepare --protocol 2`), on the generator input
  of `PROTOCOL-v2.md` ("Generator input": a truncated repository at `base_sha`, instruction files removed, a fresh
  workspace, the post-base leak check). A generator failure or a failed post-base check on any task stops the
  benchmark before any paid request; it is not worked around.
- `generic`: the runner cannot reuse the stored v2 `/init` files, so `/init` is run again, once per task, in the
  paid prepare, on the same agent images, through the same meter, with the web tools removed as in v2. Its cost is
  metered, counts against the total cap and is reported as setup cost. It is not part of any per-run figure.
- The runner records the SHA-256 of every harness file and of the `--settings` bytes inside the container before
  the agent starts and scores a trial `infra_error` on any mismatch, for every arm (v2 change log).
- `UV_NO_SYNC=1` and `--disallowedTools "WebSearch,WebFetch"` apply to every session, `/init` included, and the
  meter refuses any request that offers a web tool (v2 change log).

## Tasks and environment

- The 8 tasks of `corpus/manifest-v2.json` (checksum
  `c8bde114ef966b873cc0a13cb15e153474e5e96c3643f3ec9f3034e6104061d3`), unchanged: `pallets-click-3858`,
  `pallets-flask-6096`, `python-attrs-attrs-1593`, `expressjs-express-7366`, `pallets-click-3769`,
  `pallets-werkzeug-3298`, `pallets-werkzeug-3273`, `pallets-werkzeug-3266`.
- Model `claude-sonnet-5-5`. Claude Code 2.1.311, in the existing `olivium-bench-agent-<task>:v1` images. An image
  whose launch script is stale is rebuilt by `prepare`, as in v2; the image ids are recorded in `images.json`.
- Limits per run: 60 turns, 20 minutes, $3.
- The prompt is the same in every arm: the issue title and body, then
  `Fix this issue in the repository in the current directory.`
- Grading is unchanged from v2 (hidden tests): the agent's patch, without `CLAUDE.md`, `.claude/` and `.olivium/`,
  is applied to a clean checkout in a fresh `--network none` container, test files and test configuration are
  restored, and the real test patch is applied. Solved means every fail-to-pass test passes, no pass-to-pass test
  regresses, and the session ended `completed`.

## Run procedure

- 8 tasks × 4 arms × 3 repeats = **96 scored runs**, in one invocation into one fresh output directory
  (`value-v2r-2026-11-13`, outside the repository), with `--arms none,generic,olivium,olivium-nn --repeats 3`.
- Run order: every (task, arm, repeat) shuffled once with seed `20261108` (the runner's default for protocol 2).
  The order is written to the schedule file before the first run and is not changed.
- **Two runs at a time** (the protocol constant, as in v2).
- `infra_error` runs may be repeated, up to 3 attempts, as in v2. A run that fails because of the model or the
  harness is never repeated.
- The application snapshot that builds `olivium` and `olivium-nn` is recorded with its digests (`lib`, `config`,
  `priv/blueprints`, `bin/harnessforge`, `mix.lock`) in `app-snapshot-v2.json`. If the application source changes
  between preparation and the paid run, the paid run uses a new output directory prepared from the new source, so
  the measured exports are always those of one recorded snapshot.

## Spending and stop rules

- Paid invocations need `--paid`, `--key-file`, `--cap-usd 15`, `--run-cap-usd 3` and `--total-reserve-usd 0.25`.
  The cap of **$15 covers everything** in the output directory: the `/init` setup and all 96 runs, including
  `infra_error` attempts, because the meter replays the directory's request log when it starts. With $27.42 of the
  program's $60 spent before this version, the cap keeps the program under $60.
- Expected spend, from v2 (about $1.24 to $1.72 per arm for 24 runs, `/init` about $0.10 per task): about $6 to $9.
  Generated skills and subagents may raise the `olivium` arm's cost; the cap bounds it.
- Stop rules. No further run starts, and the operator reports instead of resuming, when any of these holds:
  1. the meter's total cap is reached (requests refused, runs `budget_exhausted`);
  2. `infra_error` attempts exceed 10% of the scheduled runs, that is more than 9 of 96 (`--max-infra-errors 9`);
  3. a web tool reached any session (existing web guard);
  4. a harness-check failure (an arm's files or `--settings` bytes did not reach the container as built);
  5. a trial reports a Claude Code version other than 2.1.311 or a main model other than `claude-sonnet-5-5`.
- Every phase other than the paid prepare (`/init`) and the paid run uses the mock meter or no model at all.
- If a benchmark bug is found after the scored run begins, all scored runs are discarded and repeated within the
  remaining cap, with an entry in the change log; runs are never re-done selectively. If the remaining cap cannot
  cover a full repeat, no result is published as a measurement, and the bug and the spend are reported.

## Before any paid request ($0)

- The protocol's SHA-256 is recorded outside the repository before the first paid request, and listed in
  `PROTOCOL-v2r.sha256`.
- Preparation at $0: material for the 8 tasks, the agent images, `none`, `olivium` and `olivium-nn` set up.
  Reported per task: the skills and subagents the `olivium` export contains, its file count and bytes, and the
  difference from `olivium-nn`.
- A mock rehearsal (`--dry-run`, mock meter, no key) into a separate directory, every arm on at least 2 tasks:
  grading, metering, hooks, harness checks, permission mode, and the first request of each arm (request capture),
  showing that the `olivium` export's skills and subagents are offered to the session and `olivium-nn` offers none.
  Mock output is stamped REHEARSAL and never published as a result.

## Metrics and analysis

Analysis script: `bench/value/analyze_v2r.py`, fixed before the paid run.

- Trial records and metrics as in v2. Token and dollar figures come from the meter.
- **Primary metrics:** total tokens per run (input + output + cache write + cache read), cost per run (USD), and
  solved (share of runs).
- **Primary comparisons:** `olivium − none`, `olivium − olivium-nn`, `olivium − generic`.
- For each task and arm, average the scored runs (3 repeats; `infra_error` rows are never scored). For each
  comparison and metric: the per-task difference, the median difference across the 8 tasks, and a percentile
  bootstrap 95% interval of that median, resampling tasks with replacement, 10,000 resamples, seed `20261108`.
- An interval that includes zero is reported as a difference the data cannot tell from no effect. No benefit is
  described that the data does not show.
- Secondary, descriptive: each token component, turns, files read outside the real fix, turns and tool calls
  before the first edit to a fixed file, regressions, lint, permission denials, Stop-hook blocks, and the use of
  generated skills and subagents (Skill and Agent/Task tool calls per run). Setup cost per arm (`/init` as metered;
  `olivium` and `olivium-nn` $0). First-request size per arm from the mock request capture.
- The report states the comparison with the published v2 results only as different runs on different days.

## Publication

The result is published whatever it is, including no effect or a negative one, under
`docs/benchmarks/value-v2r-2026-11-13/`. Numbers reach any other document only from that `results.json`. Only
references, statistics, trial summaries, charts and counts are published: no third-party source, patches, issue
text, full transcripts or local paths.

## What this cannot show

Eight development tasks the generator was tuned on, from five repositories in the same two families of tooling,
one model, one agent, bug fixes only. Three repeats per arm. An interval across 8 tasks can show a direction or a
problem; it cannot prove a general effect.

## Change log

None of this is chosen from outcome data; no paid request had been made.
